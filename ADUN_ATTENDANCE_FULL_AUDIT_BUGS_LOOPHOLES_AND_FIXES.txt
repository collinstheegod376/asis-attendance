1. EXECUTIVE SUMMARY & SYSTEM FAILURE CASCADES
================================================================================
1.1 Global Production Status & Risk Assessment
--------------------------------------------
An exhaustive, deep audit of the ADUN Smart Attendance System across all three codebases
(supabase/, student-pwa/, admin-portal/) reveals that the application is currently
INOPERABLE in a production environment and exhibits CRITICAL security, data integrity,
and workflow failure loops. While the system demonstrates sound architectural intentions
(5 verification gates, CSPRNG tokens, strict 1-device binding, geofencing, selfie proof),
critical disconnects between database migrations, Edge Functions, client state, and browser
APIs completely dismantle these protections.

1.2 The Five Critical Architecture Cascades Breaking the System
--------------------------------------------------------------
1. COMPLETE DATABASE PRIVILEGE AND RLS COLLAPSE (SEC-01, SEC-02, PERF-02)
   The second migration (20261109000000_supabase_full_seed_and_permissions.sql:13-27)
   explicitly executes "ALTER TABLE ... DISABLE ROW LEVEL SECURITY" across all 11 tables
   and grants "ALL PRIVILEGES" to public "anon" and "authenticated" roles. Any student
   possessing the public VITE_SUPABASE_ANON_KEY can execute arbitrary INSERTs into
   attendance_records, truncate or delete device_bindings, dump all user credentials
   (including bcrypt password hashes), view student PII, and purge immutable audit_logs.
   Furthermore, student-pwa/src/lib/supabase.ts:89-180 exposes direct client-side RPC
   fallbacks which bypass Edge Function cookie validation and Gate 4 checks.

2. CRASH ON SUBMISSION: 0% SUCCESS RATE FOR ALL STUDENTS (SEC-10, QA-01, PERF-01)
   In PostgreSQL function "rpc_submit_attendance" (adun_attendance_schema.sql:1381), the
   query evaluates: COALESCE(p_fingerprint_hash, p_device_info->>'fingerprint_hash',
   v_attempt.fingerprint_hash). However, table "attendance_attempts" (schema.sql:185-201)
   DOES NOT HAVE a "fingerprint_hash" column. Every single call to rpc_submit_attendance
   crashes immediately with PL/pgSQL error: record "v_attempt" has no field "fingerprint_hash".
   As a result, NO STUDENT CAN EVER RECORD ATTENDANCE against the live database.

3. LOCAL DEVICE ID PARAMETER MISMATCH & 100% 2ND-SESSION LOCKOUT (SEC-03, QA-05, PERF-04/05)
   The Student PWA sends JSON key "device_id: deviceId" to /functions/v1/device-check,
   but the Edge Function reads "body?.local_device_id". Consequently, p_local_device_id
   is always passed as NULL to rpc_device_check, storing device_bindings.device_id as NULL.
   On any subsequent session, rpc_device_check (schema.sql:1066) evaluates:
   IF v_is_ios AND (p_cookie_token_hash IS NULL OR p_local_device_id IS NULL) THEN
   RETURN BIND-204. Because p_local_device_id is null, 100% of returning iOS students
   are locked out with BIND-204 ("Unrecognized device"). Simultaneously, on Android/Desktop,
   if a student opens Incognito, p_cookie_token_hash is NULL, but because v_binding.device_id
   was saved as NULL, the device check FAILS OPEN and returns OK, allowing unlimited spoofing!

4. ADMIN PORTAL SPLIT-BRAIN MEMORY LOOP & 3-SECOND DATA ERASURE (SEC-16, QA-02/03, PERF-03)
   The Admin Portal does not write mutations (course creation, lecture sessions, roster
   imports, lecturer user management, device resets) to Supabase tables. Instead, storage.ts
   only updates browser localStorage. Concurrently, storage.ts runs syncFromSupabase()
   every 3,000 milliseconds, which performs "SELECT *" on all 10 tables and OVERWRITES
   localStorage. Every session created or device reset by a lecturer is wiped within 3 seconds.
   Additionally, syncFromSupabase overwrites every user password to "admin", allowing any
   person to log into any lecturer account with password "admin".

5. LOCATION & CAMERA GATES FAIL OPEN (SEC-07, SEC-08, SEC-09, SEC-13, PERF-08/11)
   AttendLocationPage.tsx:83-93 catches any error thrown by verifyLocation (such as server
   downtime or network block) and unconditionally executes "setVerifiedSuccess(true)",
   completely bypassing geofencing. rpc_submit_attendance does not check whether location
   verification was passed or even attempted. rpc_verify_location defaults inside_boundary
   to TRUE when campus_boundary_geojson is NULL (which is default). CameraHUD.tsx contains
   no facial recognition or liveness challenge—it merely counts 50 animation frames (0.83s)
   and snaps whatever the lens points at (including a black card or wall), while Storage RLS
   rejects all anon uploads with 403 Forbidden, which the client silently ignores.

2. PART I: APPLICATION SECURITY & ANTI-FRAUD AUDIT (AGENT 1)

2.1 Agent 1 Executive Summary
-----------------------------
- **Complete Database RLS Bypass (`CRITICAL`)**: Migration 20261109000000_supabase_full_seed_and_permissions.sql explicitly disables Row-Level Security (`DISABLE ROW LEVEL SECURITY`) on all 11 tables and grants `ALL` privileges to `anon`, allowing any student with the public `VITE_SUPABASE_ANON_KEY` to insert/delete attendance records, clear device bindings, read staff password hashes, and wipe audit logs.
- **Direct RPC Fallback & Gate Bypass (`CRITICAL`)**: All student-facing `SECURITY DEFINER` RPCs (`rpc_device_check`, `rpc_submit_attendance`, `rpc_verify_location`, `rpc_lookup_matric`) are directly callable by `anon` and used as automatic client fallbacks (supabase.ts). Calling `rpc_submit_attendance` directly bypasses the Edge Function's HttpOnly cookie verification, Gate 4 (`rpc_device_check`), and step/location enforcement entirely.
- **Broken Cookie/LocalStorage Contract & Incognito Fail-Open (`CRITICAL`)**: A parameter mismatch between `student-pwa` (`body.device_id` at supabase.ts) and `device-check` Edge Function (`body.local_device_id` at device-check/index.ts) causes `p_local_device_id` to always be `NULL` via Edge Function. This permanently blocks every iOS student on their 2nd sign-in (`BIND-204`) while simultaneously causing Incognito mode on Android/Desktop to **fail open** (`OK`) when `p_local_device_id` is passed via RPC because `v_binding.device_id` was stored as `NULL`.
- **Location & Liveness Gates Fail Open (`CRITICAL`)**: AttendLocationPage.tsx catches any `verifyLocation` error and marks location verified (`setVerifiedSuccess(true)`), `rpc_submit_attendance` never checks whether location verification occurred or passed, `rpc_verify_location` defaults `v_inside_boundary := true` when `campus_boundary_geojson IS NULL`, and CameraHUD.tsx has zero face detection or liveness checks (capturing any image after 50 frames while ignoring Storage RLS upload failures).
- **Broken Admin/Lecturer Authentication & Unauthenticated Device Reset (`CRITICAL`)**: The Admin Portal uses client-side `localStorage` auth (AuthContext.tsx), overwrites every synced user's password in `localStorage` to `'admin'` (storage.ts), dumps the entire university database into browser `localStorage`, and reset-device-binding/index.ts skips JWT verification whenever `actor_id` is supplied in the JSON request body.

DEFECT IDENTIFIER: SEC-01 [CRITICAL]
SCOPE LETTER     : G
SPEC CLAUSE      : Spec §11 / Schema §8 (RLS on all 11 tables; `anon` blocked from direct table reads/writes)
FILE REFERENCE   : 20261109000000_supabase_full_seed_and_permissions.sql:13-27
AUDIT CONFIDENCE : high
--------------------------------------------------------------------------------
VULNERABILITY DESCRIPTION & LOOPHOLE MECHANISM:
  The second migration runs `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` on all
  11 tables and `GRANT ALL ON ALL TABLES IN SCHEMA public TO anon,
  authenticated`. Any student using the public `VITE_SUPABASE_ANON_KEY` can
  read/write/delete `attendance_records`, `device_bindings`, `users` (including
  `password_hash`), `students_master` (PII), and `audit_logs`.

EXPLOITATION PROOF OF CONCEPT / REPRODUCTION SCENARIO:
  In browser DevTools on Student PWA, run `await
  supabase.from('attendance_records').insert(...)` or `await
  supabase.from('device_bindings').delete().neq('id',
  '00000000-0000-0000-0000-000000000000')`.

CONCRETE CODE / SQL REMEDIATION:
  Remove `DISABLE ROW LEVEL SECURITY` and `GRANT ALL ... TO anon` from
  `20261109000000_supabase_full_seed_and_permissions.sql`; re-enable RLS on all
  11 tables and `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon`.

AUDIT CONFIDENCE : high

VULNERABILITY DESCRIPTION & LOOPHOLE MECHANISM:

  and restrict `SECURITY DEFINER` attendance/device RPCs strictly to
  `service_role` (Edge Functions only). Also invoke `rpc_device_check` inside
  `rpc_submit_attendance` transactionally.

SCOPE LETTER     : C
SPEC CLAUSE      : Spec §6.1 / §6.3 (Incognito / Private Browsing detection and fail-closed cookie check)
FILE REFERENCE   : AttendIdentityPage.tsx:121,160, 20261108000000_adun_attendance_schema.sql:801,951,1066-1141
AUDIT CONFIDENCE : high
--------------------------------------------------------------------------------
VULNERABILITY DESCRIPTION & LOOPHOLE MECHANISM:

  Bind Student A on Android via Edge Function (`v_binding.device_id` is `NULL`).

  first-bind check) whenever `p_incognito_signal = true`, and require

  `v_binding.device_id = p_local_device_id` when `v_binding.device_id IS NOT
  NULL`) instead of skipping validation when `v_binding.device_id IS NULL`.

2.4 Security Specification Gaps
-------------------------------
1. **Shared Device Flag (`is_shared`) vs. Unique Active Fingerprint Constraint (Spec §6.1 / §6.2 vs. Schema `device_bindings`)**:
   - **Clause**: Schema defines `is_shared BOOLEAN NOT NULL DEFAULT false` on `public.device_bindings` (20261108000000_adun_attendance_schema.sql:161) and a partial unique index `CREATE UNIQUE INDEX one_active_binding_per_fingerprint ON device_bindings (fingerprint_hash) WHERE status = 'active'` (line 167).
   - **Contradiction / Gap**: Because `one_active_binding_per_fingerprint` enforces uniqueness across all `status = 'active'` rows regardless of `is_shared`, two students (e.g., siblings sharing a phone in different courses) **can never both have an active binding for the same `fingerprint_hash` at the same time**, even if an admin sets `is_shared = true`. The spec does not define how `is_shared = true` is supposed to allow legitimate multi-student use across different sessions while still blocking same-session proxy sign-ins.
2. **Reference Code Taxonomy Conflict (`BIND-200` through `BIND-206` in Spec §6.3 / §12)**:
   - **Clause**: generate_pdf.py:308-312 and 20261108000000_adun_attendance_schema.sql:810-1612 define `BIND-201` = New Device Mismatch (and also first bind at line 849), `BIND-202` = Bound to Another Student, `BIND-203` = Same-Session Collision, `BIND-204` = Unrecognized Device / Cookie Mismatch, `BIND-205` = Incognito Mode, `BIND-206` = Admin Reset. Meanwhile, AuditPage.tsx:23-34 and DeviceBindingsPage.tsx:64-120 define `BIND-201` = Initial Bound, `BIND-202` = Mismatch, `BIND-203` = Cookie Missing, `BIND-204` = Cookie Mismatch, `BIND-205` = Admin Reset, `BIND-206` = Proxy Detected.
3. **Geofence Configuration Model: Circle (`center_lat`, `center_lng`, `radius_m`) vs. GeoJSON Polygon (`campus_boundary_geojson`) (Spec §7 / §11)**:
   - **Clause**: Admin Portal SettingsPage.tsx:188-230 exposes Circle Geofencing (`campus_center_lat`, `campus_center_lng`, `campus_radius_m`) as the primary configuration and treats `campus_boundary_geojson` as optional, whereas `public.settings` (20261108000000_adun_attendance_schema.sql:238-251) and `rpc_verify_location` (lines 1227–1230) only store and evaluate `campus_boundary_geojson`.
4. **Device Binding Timing: On Matric Lookup vs. On Identity Confirmation / Final Submission (Spec §5 / §6.1)**:
   - **Clause**: Spec §5 provides a "Not you? Edit manually" flow on the identity confirmation card, while Spec §6.1 states a student's first check-in permanently binds their device to their matric number. Performing the permanent database write to `device_bindings` *before* the student confirms the "Is this you?" card means a single typo of an unbound classmate's matric number permanently binds the wrong student to the device before the user can click "Edit".

2.5 Security Scope Verification Pass List
-----------------------------------------
- **Scope A — Token CSPRNG & Length**: Session tokens are generated with `crypto.getRandomValues` (CSPRNG) at 192-bit/256-bit entropy in lecturerService.ts:30-34 and sessionService.ts:13-18.
- **Scope A — Token Hashing at Rest**: `public.lecture_sessions` stores `token_hash` (SHA-256) and `rpc_validate_session_token` (20261108000000_adun_attendance_schema.sql:543-550) looks up sessions by SHA-256 hash.

- **Scope A — Server-Side Time Window Enforcement**: `rpc_validate_session_token` (20261108000000_adun_attendance_schema.sql:560-579) uses PostgreSQL server `now()` to enforce `SESSION_NOT_STARTED`, `SESSION_CLOSED`, and `SESSION_EXPIRED`.
- **Scope A — Duplicate Final Attendance Prevention**: `public.attendance_records` enforces `CONSTRAINT unique_session_student UNIQUE (session_id, student_id)` (20261108000000_adun_attendance_schema.sql:222).

3.5 Detailed Analysis of Unreachable and Missing States
-------------------------------------------------------
1. **`/attend/confirmation` (Legitimate Post-Submission State — UNREACHABLE against Supabase)**: Because `rpc_submit_attendance` (20261108000000_adun_attendance_schema.sql:1381) references `v_attempt.fingerprint_hash` which does not exist on `attendance_attempts`, every real attendance submission crashes in PostgreSQL.
2. **All Student Verification States for Lecturer-Created Sessions (`/attend/identity` -> `/attend/confirmation` — UNREACHABLE from Lecturer QR)**: Because `LecturerService.createLectureSession` (lecturerService.ts:412-480) writes only to `admin-portal` `localStorage` (`adun_sessions`) and never inserts into Supabase `lecture_sessions` (and is wiped 3 seconds later by `syncFromSupabase`), scanning a Lecturer's Classroom Projector QR code in `student-pwa` always fails `rpc_validate_session_token` with `INVALID_TOKEN`, trapping every student at `/invalid`.
3. **`scheduled` Session State (MISSING in Portal Service & Types)**: `createLectureSession` (lecturerService.ts:450) hardcodes `status: 'active'` even when `starts_at` is in the future, and `CourseSessionsTab.tsx:205` displays future-dated sessions as `'Active Live'`.
4. **`revoked` Session State (UNREACHABLE from Lecturer/Admin UI & Indistinguishable in Student PWA)**: `admin-portal` has no UI button or `LecturerService` method to revoke a session (only `closeLectureSession`), and `rpc_validate_session_token` (20261108000000_adun_attendance_schema.sql:560) returns `'SESSION_CLOSED'` for both `'closed'` and `'revoked'`.
5. **Exact Forensic Reference Code Display on Block Pages (`BIND-20X-XXXX` — UNREACHABLE on `/block/*`)**: `rpc_device_check` and `rpc_submit_attendance` generate unique suffixed reference codes (`BIND-201-A4F2`, `BIND-202-9C1B`, `BIND-203-7D3E`), but AttendIdentityPage.tsx:165-204 and AttendVideoPage.tsx:79-97 ignore the returned `reference_code` suffix and navigate to hardcoded `?ref=BIND-201`..`?ref=BIND-205`.

3.6 QA & Workflow Specification Gaps
------------------------------------
1. **Zero-Sessions-Held Attendance Percentage Definition (Scope E / Section 12)**: The spec does not explicitly specify whether a newly created course with `0` held sessions should display `0%` or `N/A — No sessions held`. The implementation defaulted to `100%` (lecturerService.ts:540,640), which falsely marks students with 0 attendance as `100% (Exam Eligible)`.
2. **Client `localStorage` Soft-Lock Recovery After Server-Side Admin/Lecturer Reset (Scope C & F / Section 14)**: When Student A's old device is legitimately passed to Student B after an Admin reset, the spec does not define whether the client soft-lock should be overwritten automatically when the server's `rpc_device_check` authorizes the new student. Currently, the client soft-lock runs *before* contacting the server and blocks Student B.
3. **Reference Code Numbering & Suffix Format (`BIND-200` through `BIND-209`) (Scope C & F)**: The spec defines `BIND-200`..`BIND-205` for student block pages, while the Admin Portal and SQL RPCs also introduce `BIND-206`..`BIND-209` and append random 4-character hex suffixes (`BIND-201-XXXX`) in SQL without specifying whether Audit Trail filtering should match by prefix (`BIND-201`) or exact instance ID (`BIND-201-A4F2`).
4. **Course Reassignment vs Auto-Archive on Lecturer Soft-Delete (Scope F & G)**: Spec F states *"Soft-delete lecturer: courses archived or reassigned, attendance preserved"*, while Spec G states *"Lecturer deleted -> course archived, QR links behave correctly"*. The UI (LecturersPage.tsx:120) only auto-archives courses without prompting the Admin to optionally reassign active courses to another lecturer before deleting.

- **End-to-End Persistence & Attendance Submission Are Broken in Production**: (1) `rpc_submit_attendance` (20261108000000_adun_attendance_schema.sql:1381) references `v_attempt.fingerprint_hash`, a column that does not exist on `attendance_attempts`, throwing a runtime PL/pgSQL error (`record "v_attempt" has no field "fingerprint_hash"`); (2) all Admin/Lecturer Portal mutations (`createLectureSession`, `importCourseRoster`, `createCourse`, `resetDeviceBinding`, etc.) write exclusively to `localStorage` without writing to Supabase, and are overwritten every 3 seconds by `AppStorage.syncFromSupabase()` (storage.ts:88-199).
- **100% Second-Session Lockout Across All Browsers & iOS Safari (`BIND-204`)**: student-pwa/src/lib/supabase.ts:71 sends `device_id` in the request body while device-check/index.ts:34 reads `body.local_device_id` (always `null`), and the `adun_trusted_device` cookie (`SameSite=Lax`, cross-origin to `*.supabase.co`) is never sent on cross-site `fetch` `POST` calls or under iOS Safari ITP, causing `rpc_device_check` (`lines 951, 1066`) to reject 100% of returning students with `BIND-204`.
- **Migration #2 Destroys RLS, Grants `ALL` to `anon`, and Violates Zero-Demo-Data**: 20261109000000_supabase_full_seed_and_permissions.sql:13-27 disables Row-Level Security (`DISABLE ROW LEVEL SECURITY`) on all 11 tables, grants `ALL` table privileges to `anon`, and seeds demo lecturer `tega`, course `ADUN CYB 201`, and 93 students.
- **300-Student Lecture Load Collapses Under 3-Second Full-Table Polling & Base64 JSONB Bloat**: AttendVideoPage.tsx:62 embeds the entire base64 JPEG selfie (~80–150 KB) into `attendance_records.device_info` JSONB, while `admin-portal` polls `SELECT *` on all 10 tables every 3 seconds (storage.ts:88-199), generating ~30 MB every 3 seconds (~80 Mbps per open admin/lecturer tab) at 300 records.
- **PWA Offline/Install, Camera Lifecycle, Excel Math, and Reference Code Integrity Fail Spec**: Service Worker `navigateFallbackDenylist` blocks `/join/*` and `/attend/*` from ever reaching `/offline` (student-pwa/vite.config.ts:45), CameraHUD.tsx fakes face detection via a 50-frame counter and leaves the camera stream hot after capture, Excel export awards `100%` attendance when `0` sessions are held (lecturerService.ts:540,640) and omits signed selfie URLs, and `BIND-201` through `BIND-206` have conflicting definitions across SQL, Edge Functions, Student PWA, and Admin Portal.

4.6 Data Integrity, PWA & Hardware Specification Gaps
-----------------------------------------------------
1. **Cross-Origin Architecture vs. First-Party Cookie & iOS ITP Requirement**: The specification mandates an `HttpOnly; Secure; SameSite=Lax` cookie (`adun_trusted_device`) set by Supabase Edge Functions AND mandates strict iOS continuity (`p_cookie_token_hash IS NOT NULL AND p_local_device_id IS NOT NULL` in `rpc_device_check`). However, when the Student PWA is hosted on its own domain (e.g., `attend.adun.edu.ng` or `localhost:5173`) and calls `https://<project>.supabase.co/functions/v1/device-check` via `fetch(..., { credentials: 'include' })`, browsers treat the cookie as a **cross-site cookie**. Under RFC 6265bis (`SameSite=Lax` never sent on cross-site `POST`) and Apple WebKit ITP (all third-party cookies blocked), the cookie is never transmitted unless `/functions/v1/*` is reverse-proxied under the exact same origin as the PWA.
2. **Safari 16+ / iOS WebClip Storage Partitioning vs. Single-Device Binding**: On iOS, if a student scans the first QR code in Safari and later installs the PWA to their Home Screen, iOS creates an isolated storage partition for the Home Screen WebClip (`localStorage` and cookies are not shared with Safari). The spec encourages PWA installation (`display: standalone`) while simultaneously treating a missing `local_device_id`/cookie on the same hardware fingerprint as a `BIND-204` security violation requiring an Admin/Lecturer reset.
3. **Reference Code Suffixes & Numbering (`BIND-201` through `BIND-209`)**: The spec defines bare codes `BIND-201` through `BIND-205` for student-facing blocks, omits standard codes for Admin Reset, Shared Device Exception, and Device Revocation, and does not specify whether `device_events.reference_code` should store bare codes (`BIND-201`) or suffixed codes (`BIND-201-A1B2`).
4. **Zero-Session Course Attendance Percentage Definition**: The spec defines the 75% exam eligibility threshold (`>= 75%`) and states that `Present` and `Late` both count toward attendance, but does not explicitly state whether a newly created course with `0` held sessions should display `0%` or `N/A` (leading the developer to default to `100%`).
5. **Lecturer Course Roster Upload Policy for Unmatched Matric Numbers**: The spec states that Admins manage `students_master` while Lecturers upload course rosters (`course_roster`), but `RosterService` rejects unmatched matrics while `LecturerService` auto-creates them in `students_master`.
